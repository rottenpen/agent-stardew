# 研发与贡献体验

研发者通过源码工作区运行、修改和验证 agent-stardew。默认配置组装好主 Agent 与开发 Agent；贡献者通过 skill、共享协议和 Mod 增加能力，Agent 产生的改动也走同一套构建与验收流程。普通用户使用[桌面安装包](desktop-distribution.md)，源码命令属于研发入口。

本文规定完整的使用与贡献体验。M0 已提供 `setup`、`dev`、`check`、`doctor`、模拟服务及测试入口，当前安装步骤见 [README](../README.md)，实际验证范围见[验证记录](verification.md)。桌面界面、Agent 协作、版本启用和恢复仍按后续阶段实现，机制见[持续游玩方案](self-improving-agent.md)。

## 1. 研发交付物与扩展入口

| 交付物 | 使用方式 | 负责的事情 |
|---|---|---|
| 本仓库 | 获取一个已发布版本的源码，执行快速开始 | 完整的持续游玩、自主开发及贡献环境 |
| `dsh-stardew` 组合包 | 通过 dsh 原生插件命令安装 | 游戏工具、角色默认配置和任务控制；两个插件入口由包统一组装 |
| `agent-stardew` CLI 与 Mod 发布包 | 独立观察、操作与排查游戏接入 | 稳定的动作语义、JSON 结果、游戏连接和诊断 |

研发指南使用完整源码工作区，包含 CLI、Mod、测试与可复现的构建环境。已安装 dsh 的研发者也可单独接入组合包，再绑定源码工作区。桌面版自动准备布局一致的托管工作区，复用这些代码和脚本。

首次使用只需理解项目目录、游戏连接和目标。主 Agent 默认按需启动一个开发 Agent；独立验证按改动触发。角色数量、子会话标识与内部工具属于进阶说明。

## 2. 源码快速开始以首次取得真实快照为终点

前置条件是安装发布说明指定的 Node.js、pnpm 和 dsh，并准备自己的星露谷与 SMAPI。模型及凭据沿用 dsh 的配置入口。首个发行版的实机支持范围以 macOS 验收结果为准；其他平台分别标注测试状态。

以下是研发目标体验；完整的分支、测试和 PR 要求见[贡献指南](../CONTRIBUTING.md)：

```sh
git clone https://github.com/rottenpen/agent-stardew.git
cd agent-stardew
pnpm install --frozen-lockfile
pnpm run setup
pnpm run doctor
pnpm dev
```

| 命令 | 必须做到 |
|---|---|
| `pnpm run setup` | 检测路径与依赖，准备匹配源码版本的 Mod 和运行产物，创建项目专用 dsh profile，安装组合包，打印配置与安装位置 |
| `pnpm run doctor` | 一次列出环境、dsh 加载、游戏连接、协议兼容、存档与自主开发条件；区分可游玩和可开发，逐项给出修复办法 |
| `pnpm dev` | 从项目工作区启动配置好的 dsh 界面；展示连接状态、当前版本和能力，接收游戏目标 |

`setup` 重复运行保持幂等，保留已有设置和版本备份，只管理登记为本项目所有的 profile、插件及 Mod 目录。游戏路径自动探测；找不到或存在多个安装时允许显式指定。游戏尚未启动与依赖缺失分别报告。

运行使用固定版本的构建目录，候选在独立目录中编译。启动命令负责准备和启动；Agent 循环、会话与目标续行由 dsh 运行。首次进入 dsh 界面时，按其原生流程选择项目工作区和模型，执行“观察当前农场”，看到真实日期、位置与背包才算接入成功。

普通游玩可使用与版本匹配的预构建 Mod；自主修改 Mod 时，`doctor` 还需确认 .NET SDK、游戏引用和本地构建可用。实机示例使用专用测试存档，准备说明随仓库交付。

## 3. 配置集中在 dsh，机器信息保存在本地

| 信息 | 来源与归属 |
|---|---|
| 模型、凭据、会话与通用权限 | dsh 现有配置与界面；项目沿用所选模型 |
| 游戏连接、调用时限、开发预算、角色工具范围 | 插件的类型化 `Config` 和默认 bundle patch；高级定制使用 dsh profile patch |
| 游戏目录、可选的 SDK 路径 | 自动探测与 `.env.example` 中列出的本地覆盖项，真实值保存在忽略的本地文件 |
| 工作区与运行目录 | 根据启动目录解析，运行时生成并记录绝对路径 |

同一设置保持一个生效来源，`doctor` 显示实际值及其来源，凭据只显示是否可用。启动需要的最低配置由默认值承担；修改角色指令或模型走正常的 dsh 配置流程。

源码中的路径按项目根目录或包位置解析。发布依赖声明经过验证的 dsh 版本范围，并通过正常安装解析；与本机 dsh 源码的链接只用于联合开发。

dsh 的安装与加载集成采用本机核对过的原生入口：

```sh
dsh --profile <项目profile> --from-default-profile web --dump-config
dsh plugin --profile <项目profile> add <组合包位置>
dsh --profile <项目profile>
```

上面是 `setup` 和启动脚本的实现依据，首次创建后复用已登记的 profile。组合包位置可为构建好的本地目录或已发布包；源码模式与发行包模式分别测试。当前核查基线为 dsh `aa8262ec091698bae9a6b04773a6b5b06ad4aef2`，正式兼容性声明以集成测试结果为准。

## 4. 按贡献目标组织接口和示例

| 要贡献的能力 | 修改入口 | 最小验证 |
|---|---|---|
| 原子技能、失败恢复、操作顺序 | `packages/dsh-plugin/src/agent/skills.ts` | 一个正常任务和一个不同起始状态；说明结果判据 |
| dsh 聊天使用方式与工具说明 | `packages/dsh-plugin/skills/stardew/SKILL.md`、`packages/dsh-plugin/src/index.ts` | 工具 schema、调用和取消测试 |
| 新的基础动作或观察字段 | `packages/protocol` 的契约、Mod 处理器、必要的 CLI 适配 | 请求与结果样例、失败样例、实机状态变化 |
| 委派、候选验证、启用或恢复 | `packages/dsh-plugin/src/agent/` | 不调用模型的状态与生命周期测试；涉及游戏的部分追加实测 |

共享协议集中定义请求、结果、约束、错误与描述。dsh 工具参数从契约派生；CLI 只维护命令行表达与协议参数的映射。C# 实现使用同一组协议样例检查兼容性。新增动作时，贡献者可以沿示例找到每个必需修改点。

先提供一个完整的农务 skill 示例和一个完整的基础动作示例，包含源码、失败用例和验证方法。扩展入口使用现有的 Markdown、TypeScript 与 C# 文件，能力能通过文件查找直接定位。

内部协作工具由组合包注册；用户描述目标即可驱动它们。开发者文档公开工具契约和运行记录格式，方便排查与贡献；具体状态存储、调度和发布模块保持包内实现。

开发 Agent 与人类贡献者使用同样的脚本、测试和完成标准。Agent 改动保留基线、补丁和验证结果，整理后可以进入常规 PR 流程；本地能力积累与上游发行版本分别记录。

## 5. 没有游戏也能完成多数开发检查

提供轻量的模拟协议服务和固定样例，覆盖成功、资源不足、引用过期、连接断开与取消。模拟模式启动只准备 dsh profile 和 TypeScript 产物，跳过游戏路径与 Mod 安装检查。模拟运行始终标注 `mock`，使用独立记录目录，结果不能满足实机验收条件。

| 入口 | 环境要求 | 检查范围 |
|---|---|---|
| `pnpm check` | Node.js 与 pnpm | 类型检查、TypeScript 构建、契约和状态测试；不使用游戏或模型凭据 |
| `pnpm dev --mock` | dsh；需要实际推理时配置模型 | 用模拟协议服务调试工具展示、错误处理与协作流程 |
| `pnpm test:dsh` | 兼容的 dsh 发行版本 | 真实加载组合包、工具 schema、调用与取消；通过固定测试驱动避免模型波动 |
| `pnpm run dev:desktop`（待实现） | 桌面构建依赖 | 用独立开发数据目录运行同一业务 UI，验证引导与托管工作区 |
| `pnpm build:mod` | .NET SDK、游戏与 SMAPI 引用 | 构建 Mod，不作为公共基础检查的前置条件 |
| `pnpm test:game` | 已启动游戏及已加载存档 | 当前仅只读快照；完整任务判定、版本启用及恢复待实现 |

公共 CI 运行确定性基础检查和发行包安装检查。游戏测试在具备游戏环境的机器运行，报告实际执行版本与次数。界面中明确区分自动化检查、模拟协议和真实游戏结果。

## 6. 调试从一个失败编号开始

主界面复用 dsh 会话与工具结果卡片，显示当前目标、游戏状态、正在补充的能力、验证阶段和实际启用版本。默认给出可读摘要，展开后再看调用与开发细节。

每次运行在 `work/runs/<run-id>/` 保存摘要、结构化事件和候选证据引用。一次失败应能定位到调用编号、错误码、前后快照、版本及下一步处理。CLI 的 `--json` 继续提供稳定机器输出。

例如 Mod 未连接时，诊断应同时说明探测的地址、是否发现安装文件，以及下一步是启动 SMAPI 还是修正配置。开发失败时，说明候选停在哪一阶段、运行版本是否变化、原目标还能推进哪些步骤。

Issue 模板要求版本、复现步骤、诊断结果和相关事件。分享材料排除凭据、个人绝对路径与原始存档；完整运行数据保留本地。软件版本恢复与游戏存档恢复分别展示结果。

## 7. 以外部使用者完成任务作为发行验收

README 首屏分别提供“下载安装”和“参与开发”入口，展示实际开发状态及已验证的平台和版本。贡献指南按“改 skill、加动作、改协作”导航，并给出对应测试命令。公开文档提供英文入口与中文说明，示例和命令来自同一份已验证契约。

研发发布包括预构建 CLI／组合包、Mod 压缩包、匹配的源码标签、依赖与协议兼容信息，以及项目许可证和第三方归属说明。打包后检查 `workspace:*` 已转换为可安装依赖，运行入口、skill 资源和类型声明齐全。安装与加载测试从 tarball 开始，在没有本仓库及 dsh 源码链接的环境中运行。桌面维护者通过拟定的 `pnpm run package:desktop` 准备安装包，单独验证内置依赖、签名、升级与用户流程。

首个可用发行版的 DX 验收目标：

- 前置依赖就绪后，外部研发者按贡献指南在 15 分钟内取得第一份真实快照；下载等待单独记录。
- 贡献者不安装游戏、不配置模型，也能完成一次 `pnpm check`。
- 新增农务 skill 有可直接复制的完整示例；新增基础动作能从文档找到全部契约、实现和测试入口。
- 同一个候选可以由人或 Agent 验证，报告绑定实际源码与构建版本。
- 安装失败有明确诊断；重复 setup 不破坏已有配置；源码与发行包两条路径都通过加载检查。

以上是完整发行验收目标。M0 的协议、模拟测试、dsh 加载与取消、安装诊断和发行包检查已落地；首次真实快照及完整农务流程仍需在正常刷新窗口和专用存档中验收，再用同样的贡献流程实现 skill 自修复。
