# 持续游玩中的能力开发

Jev 控制器负责游戏运行。出现现有 CLI 无法完成的操作时，把目标、观察和失败证据交给 dsh 开发 Agent；候选通过验证并实际启用后，控制器重新观察并继续目标。

本流程是后续开发阶段，尚未实现自动委派、安装和恢复。当前自主游玩入口及验收见 [Jev 运行设计](jev-runtime.md) 和 [SPEC](../SPEC.md)。

## 角色与控制权

| 部分 | 职责 |
| --- | --- |
| Jev 控制器 | 维护游戏进度，发现停滞与缺失操作，持续执行当前可用动作 |
| dsh 开发 Agent | 根据明确证据诊断，修改候选源码或决策规则，构建并提交验证结果 |
| 任务控制层 | 关联原目标、候选版本和测试，安排游戏验证与软件启用窗口 |
| 独立验证 | 跨层改动、结果不明或重复失败时按需检查固定候选 |

一个游戏实例同一时刻只有一个写控制者。离线开发可与不受影响的游玩并行；实机验证与版本切换前先暂停 Jev 控制器并等在途动作停稳。暂停 Agent 与暂停游戏时钟是不同能力。

## 缺口记录必须可复现

每项记录包含用户目标与修订、游戏实例与存档身份、当前场景、前后快照、动作与错误、候选集合、模型实际选择、预期效果和成功判据。

恢复策略先处理已有能力能够解决的问题：过期引用重新观察、距离不足先靠近、阻挡后改路。相同前提重复失败或能力列表明确缺少操作时，形成开发任务。提示词不能替代缺失的游戏动作接口。

| 缺口 | 修改层与验证重点 |
| --- | --- |
| 现场候选遗漏 | 候选生成器与观察字段；改变起点、槽位和已有进度后仍正确 |
| Jev 选择持续无效 | 问题定义、上下文和探索记忆；根据真实轨迹验证目标进展 |
| CLI 参数或结果不足 | CLI、协议与插件适配；共享语义、结果 schema 和取消 |
| 游戏操作缺失 | Mod、协议与 CLI；验证资源消耗与实际游戏变化 |
| 候选无法启用或恢复 | 构建、版本标识、安装和恢复流程；核对实际运行版本 |

## 开发、验证、启用与恢复

1. 为缺口建立独立候选目录，保留源码基线、目标修订和复现证据。
2. 开发 Agent 修改候选，提交源码／构建哈希、测试结果及待实机验证项。
3. 分别记录自动化检查、模拟协议、真实模型请求和游戏实测。报告绑定固定候选哈希。
4. 暂停控制器，安排唯一游戏实例的验证窗口。实测使用专用存档与备份。
5. 核对目标仍有效且候选满足判据，再启用软件版本。
6. 重新读取游戏状态、重建引用并核验进度，接续原目标。

验证失败、任务取消或目标修订过期时不启用候选。软件回退不会撤销已经发生的游戏动作。记录放在 `work/runs/`，源码、测试与文档保存在本仓库。

## 不同层的更新方式

| 更新对象 | 启用要求 |
| --- | --- |
| 决策规则与上下文 | 绑定版本，在动作间隙切换；后续请求采用新版本 |
| CLI | 构建完整候选，验证后切换；下一次子进程读取新入口 |
| dsh 插件 | 先停稳控制器，重建注册和宿主资源，再从新观察恢复 |
| SMAPI Mod | 正常保存并退出游戏，备份和替换构建，重启并加载指定存档 |

存档点必须符合原目标的时间约束，不能为了安装更新擅自跨天。跨游戏重启的自动恢复需要稳定存档身份；当前协议的 instanceId 与 saveGeneration 只标识本次加载。

## 后续验收顺序

| 阶段 | 通过条件 |
| --- | --- |
| 可靠自主游玩 | Jev 运行设计的 J1–J4 完成；专用存档实机证据齐全 |
| 修复一个真实缺口 | 从运行记录复现并修改候选，启用后完成原目标；新任务可复用 |
| 补齐一个基础动作 | 观察、协议、CLI、Mod 的跨层实现通过分类验证及实机结果核验 |
| 连续游玩与复用 | 在多日目标中复用已补能力，记录所有调用成本、停顿和人工介入 |

具体缺口按实际任务选择，例如缺种子时购买或从容器取物。按现有事实选题，不通过删除能力制造开发任务。
