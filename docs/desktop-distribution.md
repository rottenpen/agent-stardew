# 研发与桌面用户的分层交付

同一套游戏能力与自主开发流程，提供源码工作区和桌面安装包两种入口。研发者显式管理代码、测试和构建；普通用户安装应用、配置模型 Key，由应用准备游戏连接、能力工作区和运行环境。

本文是待实现方案。2026-09-17 已核查下列项目的公开文档、源码接口和 Release 资产；尚未安装运行这些桌面产品，也未验证本项目的桌面兼容性。研发步骤见[研发与贡献体验](developer-experience.md)，Agent 行为见[持续游玩方案](self-improving-agent.md)。

## 1. 两种入口共用一套能力

| 维度 | 研发者 | 普通用户 |
|---|---|---|
| 获取方式 | Git 仓库、源码标签、开发依赖 | 本项目的 macOS 安装包；Windows 在实机验证后发布 |
| 初始操作 | 安装依赖，运行 setup、检查与开发脚本 | 填模型 Key，确认检测到的游戏，开始任务 |
| dsh 入口 | 普通 Web profile，桌面调试按需启动 | 内置运行时和预配置桌面界面 |
| 源码与技能 | 研发者打开并修改工作区 | 应用自动准备可写的能力工作区，Agent 在其中开发 |
| 构建环境 | 明确的 Node.js、pnpm、.NET 依赖与命令 | 应用内置或自动准备锁定版本的工具链 |
| 运行反馈 | 工具调用、候选 diff、测试与诊断记录 | 游戏进度、当前目标、学会的能力、需要处理的问题 |
| 交付改动 | 本地构建、测试、PR 和发行 | 自动验证后启用本地能力；应用升级保留积累 |

共享层包含协议、CLI、Mod、skills 和 dsh 中的任务控制。主 Agent、开发 Agent 与验证流程使用同一实现，两种入口的区别集中在环境准备、界面和发行方式。

## 2. 桌面与 UI 选型

建议以官方 dsh Web UI 为界面基础，增加星露谷业务插件；桌面宿主优先验证 `anywhere-labs/dsh-desktop` 的可发布版本。它的公开 profile 与包管理服务适合接入候选构建。独立安装包使用本项目的名称、默认配置和发行资源。

| 候选 | 核查到的内容 | 本项目的采用判断 |
|---|---|---|
| [官方 Web UI 与 Desktop](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/desktop/README.md) | Web UI 提供模型设置、会话与工具展示；Desktop 源码有 Electron 壳、内置 Node.js／pnpm、离线依赖准备和版本激活机制 | UI 与运行时契约的基础；桌面代码也可作为打包实现参考。Desktop 应用包为 private，需要源码级集成 |
| [anywhere-labs/dsh-desktop](https://github.com/anywhere-labs/dsh-desktop) | [v2.0.10](https://github.com/anywhere-labs/dsh-desktop/releases/tag/v2.0.10) 于 2026-09-13 发布 Windows x64 EXE、macOS Universal DMG；源码公开 Desktop 插件服务 | 桌面宿主的首选验证对象，结合其插件接口开发产品发行层 |
| [dataelement/dsh-desktop](https://github.com/dataelement/dsh-desktop) | [v0.9.0](https://github.com/dataelement/dsh-desktop/releases/tag/v0.9.0) 于 2026-09-15 发布 macOS arm64／x64 和 Windows x64 资产；提供模型设置、恢复界面与 `.dshpreset` 导入导出 | 可作为兼容宿主，参考其首次使用和故障恢复流程；预设包不携带游戏源码工作区，仍需本项目的安装准备 |
| [hongfeiyucode/deepseek-harness-desktop](https://github.com/hongfeiyucode/deepseek-harness-desktop) | 已有捆绑 dsh 的 Electron 壳与多平台安装资产；README 列出未签名及应用内更新限制 | 适合参考较小的启动与打包实现；面向普通用户的发行还需补齐相应环节 |

上表的版本号表示实际查询到的发行记录；源码接口核查使用各仓库当时的提交，不代表全部接口都已包含在该 Release 中。选型依据是复用成本、公开接口与发行证据，界面易用性需要通过安装试用补证。

### 使用已公开的桌面接口

anywhere-labs 的 [插件文档](https://github.com/anywhere-labs/dsh-desktop/blob/01fa59e6688d82fa34b59fc507e3a6f5d695fa17/docs/plugin-development.md) 明确区分普通 dsh 插件与 Desktop 服务：

- 游戏与 Agent 插件依赖官方 dsh 契约，继续在普通 Web profile 中运行。
- Desktop 适配使用 `desktopProfiles` 取得实际 profile，使用 `desktopPnpm` 调用宿主管理的工具链；候选构建显式指定候选目录。
- 业务界面通过 dsh 的客户端插件、RPC 与 slot 接入。Desktop 服务按环境可选挂载，核心包保持独立。

该提交的 `dsh-community-fabric` 仍是 Draft，正式依赖使用已公开并验证的服务。当前本项目核查的 dsh 为 `0.1.5-rc.1`，候选桌面源码已涉及 `0.1.5-rc.2` 和独立 beta 通道；集成时锁定完整版本组合并重新验证。

第一轮桌面选型验收必须通过：加载本项目插件并获得真实快照、显示子 Agent 进度、用内置工具链在候选目录构建、关闭重开后保留 Key 与能力工作区。通过后再锁定用于本项目发行的版本。

## 3. 普通用户的首次使用流程

目标路径为：下载安装 → 填入 Key → 自动检查游戏环境 → 开始任务。用户已有受支持的星露谷安装；游戏目录探测失败时，通过文件选择器指定。操作系统需要的授权在原生界面完成。

| 步骤 | 界面呈现 | 应用负责 |
|---|---|---|
| 连接模型 | 默认提供方只填 Key，显示连接检查结果；自定义服务可展开模型与地址 | 通过 dsh 的凭据和模型设置接口保存与验证配置 |
| 连接游戏 | 显示找到的游戏、SMAPI 与 Mod 状态；必要时提供“准备游戏环境” | 探测路径、检查兼容性、准备 Mod、保留已有文件备份 |
| 准备能力 | 显示准备进度及可用状态 | 创建托管源码工作区，准备运行版本及自主开发需要的工具链 |
| 开始游玩 | 输入目标，或选择“照料农场”等示例 | 启动或连接游戏，选择明确的存档，创建主 Agent 任务 |

SMAPI 官方文档提供 `--install` 与 `--game-path` 参数，可用于预选安装动作和路径；它们不等于完全静默安装。安装器的剩余交互和系统提示需在目标平台实测，未完成时在引导页明确显示。[SMAPI 安装器参数](https://github.com/Pathoschild/SMAPI/blob/develop/docs/technical/smapi.md)

因此，“只填 Key”的验收以游戏已安装、自动检测和组件准备成功为前提。缺失的准备工作由应用引导完成，普通用户无需打开终端、编辑 YAML 或手工寻找 Mod DLL。

## 4. 普通用户仍能让 Agent 自主补能力

桌面包同时交付可运行构建和对应的源码模板。首次启动在本产品的应用数据目录中展开能力工作区，布局与研发仓库一致，包含源码、`.agents/skills/`、测试和构建脚本。dsh 默认绑定该工作区。

| 内容 | 存放位置与更新方式 |
|---|---|
| 桌面壳、固定版本 dsh、默认运行资源 | 应用安装目录；随正式产品版本发布 |
| Key、模型设置、会话 | 本产品独立的 dsh 数据目录，由既有服务管理 |
| 可修改源码与积累的 skill | 托管能力工作区；保留基线和本地改动 |
| 候选、测试记录、可运行版本 | 工作区的 `work/`；分别保存并核对哈希 |
| .NET SDK 等自主开发组件 | 应用管理的工具链目录；按锁定版本准备，显示下载与失败状态 |

Node.js、包管理器、dsh、预构建 CLI、Mod 与默认 skill 随安装包提供。自主构建还需要源码依赖、TypeScript 工具链和 .NET SDK；安装准备自动安装或复用经校验的组件。若版本流程使用 Git，则同时准备对应工具。不得只捆绑 .NET runtime 就声称支持修改 Mod。

Agent 在工作区中修改 skill／CLI／Mod，通过与研发者相同的检查后启用候选。签名应用内的资源保持完整；本地能力通过独立运行版本加载。尚未准备好某项工具链时，明确显示其状态，并继续提供已经可用的游玩能力。

完整桌面验收包括一次自动修复 skill 和一次自动构建 CLI 或 Mod。两次任务都不能要求用户手动安装 SDK、执行构建命令或复制产物。

## 5. 用户界面围绕游戏任务组织

| 界面 | 默认显示 |
|---|---|
| 首次设置 | Key、游戏检测和准备状态 |
| 农场与当前任务 | 游戏日期、体力、位置、目标进度、开始／暂停／停止 |
| 能力记录 | 正在解决的问题、已经学会的能力、验证结果；需要时展开改动与日志 |
| 设置与诊断 | 模型、开发预算、游戏连接、版本、恢复入口 |

业务 UI 作为普通 dsh 客户端插件交付，源码开发和桌面发行共用。底层会话、模型设置、工具结果展示沿用 dsh；主界面默认打开本项目的业务面板和工作区。工具名、子 Agent ID、候选哈希保留在详情中。

界面配套插画、应用图标和游戏资源的分工见[视觉素材规划](visual-assets.md)，首批母图位于 `assets/visual/`。

建议新增的文件落点：

| 位置（待实现） | 职责 |
|---|---|
| `packages/dsh-ui/` | 星露谷业务界面、状态展示与 dsh 客户端接入 |
| `apps/desktop/` | 桌面宿主集成、品牌资源、首次启动、托管工作区与安装包配置 |
| `scripts/` | 研发与安装准备共用的探测、构建、校验及版本准备逻辑 |
| 现有 `packages/` 与 `mods/` | 共享游戏能力、Agent 控制和验证实现 |

业务 UI 调用共享控制服务，所有游戏写操作继续由主 Agent 的调度入口管理。开始、暂停和取消必须作用于真实运行任务，界面显示取自结构化状态。

## 6. 应用升级保留已经学会的能力

正式产品版本绑定桌面宿主、dsh、项目插件、协议、CLI 和 Mod 的已验证组合。社区宿主有新版本时，先进入兼容性测试，再发布本产品的更新。

安装器与更新过程保留独立数据目录、源码基线、本地 skill、Key 和存档备份。能力与新基线发生冲突时，保留旧运行版本并在候选目录验证迁移；失败记录可在界面查看。

软件回退和游戏存档恢复分别处理。Mod 切换遵守已确认的游戏保存点与测试窗口；已有用户存档不作为可丢弃测试数据。整应用更新在任务可暂停的时机执行；重启后通过真实用户的“继续任务”操作恢复 dsh goal，不能将会话恢复直接算作目标已续行。

## 7. 两条交付路径分别验收

研发验收关注：无游戏的基础检查、明确的扩展入口、可复现的构建、桌面调试与发行包测试。具体命令见[研发与贡献体验](developer-experience.md)。

普通用户验收使用一台没有 Node.js、pnpm、dsh 和 .NET SDK 的干净环境，在已有受支持游戏的条件下完成：

1. 安装并打开应用，填 Key，通过连接检测。
2. 完成引导中的游戏准备，取得真实快照并执行一个明确的游戏任务。
3. Agent 发现能力缺口，自主修改、验证并启用能力，继续原任务。
4. 关闭重开后，Key、会话与新增能力仍可用；目标通过真实恢复入口继续。
5. 升级或一次失败恢复后，原有用户存档和已验证能力保持可核对。

首个样机先验证桌面装载、Key 设置、游戏准备、真实快照和托管工作区；随后接入 skill 自修复，再验证自动准备工具链后的跨层修改。模拟测试与真实游戏测试分别记录，安装包签名和平台实测完成后再声明相应平台可直接使用。
